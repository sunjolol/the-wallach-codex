## Why v1.0 looks like this

The parent project's user explicitly named the failure mode this brain file is designed to avoid:

> "I wrote the current.md (brain) file without true understanding of how Claude LIKES these things to be structured, I just sorta vibed it out and never went back and audited/refined it... we've definitely run into issues where Claude has had trouble translating current.md brain commands into actionable items that caused Claude to actually operate well and do principled development."

The fix in v1.0: **action-language with trigger / action / verify format on every binding rule**. Not "discipline X is important" but "WHEN X happens, DO Y, VERIFY Z, COMMON FAILURE W". Each rule has a verification step the agent itself can run to confirm it followed the rule. Without verification, rules become aspirational.

Plus: each anti-pitfall section names the specific incident from the parent project that earned the rule. Not abstract warnings — pattern matching against real, expensive failures.

## Inheritance from parent project

The parent project's saga / lessons / decisions / operating-protocols are NOT inherited by porting. Each new project's discipline is rebuilt from this brain. What IS inherited:

- The disciplines themselves (closing-move-atomic, paired-write integrity, chokepoint pattern, Living the Logos).
- The Tacitus three-mode architecture (Cura / Vision / Aegis).
- The companion-file structure (engineering-doctrine.md, paired-write-catalog.md, etc.) — as TEMPLATES.
- The integrity tooling pattern (invariants.py, safe_write.py, catchup_seal.py) — though the actual implementations may need re-porting from parent-project root.

What is NOT inherited:

- Parent-project domain (health, Wallach corpus, Youngevity).
- Parent-project memory (saga history, lessons earned).
- Parent-project tooling that's domain-specific (label_scorer, conflict_detector, lab_interpreter, etc.).

## Known v1.0 limitations

1. **Tooling location.** `tools/safe_write.py`, `tools/invariants.py`, `tools/catchup_seal.py` currently live at parent-project root, NOT inside `tacitus/`. When porting, the user must either copy these separately OR rebuild from the patterns documented in the brain. Filed for user decision in CHANGELOG.

2. **Tacitus prompts carry parent-project assumptions.** `tacitus/prompts/{cura,vision,aegis}.md` reference Wallach-domain concepts. §17 of the brain instructs the user to re-program these on first run; no automated stripping is provided.

3. **The brain is not itself audit-able yet.** No invariant checks the brain's internal consistency (e.g., every section reference resolves, every companion-file path exists). This is a Round 2 candidate.

4. **No empirical track record.** The brain has been authored but not yet tested against a real port. The first port will surface gaps. Plan to refine in v1.1 based on first-port findings.

## Refinement protocol

Brain updates go through saga-logged rounds with closing-move-atomic discipline. Editing `current.md` uses `safe_write.py` (the brain is a project file under §17's Edit ban). New version notes file per bump: `tacitus/brain/versions/v<N.M>-<date>-<slug>.md`. CHANGELOG entry. Saga round entry per §10.

The brain's first job is to be FOLLOWED. The second is to be REFINED.
