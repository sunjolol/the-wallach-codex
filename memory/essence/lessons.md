## Wallach corpus quirks

**Substance positions are dose/source/context, not monolithic good/bad.** This is the single most important pattern. Wallach can call fluoride essential (supplement table, ~20 mg/day) AND say *"eliminate fluoride!!!"* (rhetorical, about uncontrolled industrial dosing in tap water) AND treat tea favorably (dietary source). All three are consistent when decomposed by the four axes (substance / dose / source / context). Same pattern applies to salt, cholesterol, fats, and likely other substances we haven't tested yet.

**Books are co-authored with Ma Lan, MD.** Strong rhetorical passages (especially "eliminate!!!" with multiple exclamation marks, political framings) may carry more of her voice than Wallach's. Supplement tables, dosage programs, and operational protocols are more reliably his — they reflect what he actually recommends people *do*.

**YouTube auto-captions have no speaker tags.** In any video with multiple speakers (interview format, Daily with Doc + Becca, Ask Doc Live callers, Alex Jones-style co-host), attribution is uncertain unless verifiable by content style. Signature Wallach: hair analysis recommendation, "90 essential nutrients" framing, beef-farm-in-Missouri anecdote, "dead doctors don't lie" rhetoric. Conspiracy/political framing is more likely the co-speaker.

**Show titles lie.** A YouTube video titled "Dr. Joel Wallach — Topic X" doesn't mean Wallach speaks on X. Verify by reading the actual transcript, not the title.

**Dead-air episodes exist in the podcast feed.** Whisper produces ~100 words of dots when an episode is silent/music-only. Threshold: episodes under 500 real words are likely dead air; flag as Exclude, don't pollute usable corpus.

## Methodology lessons (about how to reason over this corpus)

- **Read whole sections, not snippets.** 25-line context windows around a hit miss tables, lists, and supplement programs. Minimum 2,000-char windows or full chapter for any controversial topic.
- **Structured data > prose rhetoric.** Tables, supplement programs, dose-and-frequency lists are the operational position. Polemical prose is commentary on top of it.
- **Integrate; don't flip.** When new evidence challenges a prior answer, integrate. Don't abandon prior evidence. State what each piece still supports after the update.
- **Read user-provided sources before responding.** Always. Inexcusable to dismiss without reading.
- **Vision-reads of long list graphics aren't reliable in isolation.** Cross-check element counts against book sources before treating the list as canonical. The original TRANSCRIPTIONS.md 90-nutrients-front read had 59 minerals not 60 (Niobium dropped); only caught when a second source — the Dirobi/Harada PNG — disagreed on count and Hell's Kitchen + Rare Earths + Dead Doctors Don't Lie confirmed Niobium is canonical. Pattern: if the source claims "60 X" or "16 Y", count what you transcribed. If it doesn't match the stated total, find the missing element before publishing.
- **Presentation can destroy correct reasoning.** A substance-correct answer the user skims delivers less value than a tight plain-English bottom line with scannable exceptions for the contexts that flip the default. Lead direct; surface exception cases proactively; offer depth instead of force-feeding it. If gotcha follow-ups keep being needed, the original answer wasn't doing its job.

## File hygiene at the time of merge (2026-06-13 at ~3:00 PM, post-v2.8)

**Pattern observed.** Brain v2.7 was drafted in a scratchpad file (`brain/pending-v2.7-additions.md`) during Phase A and committed to `brain/current.md` during Phase C. The committal happened; the scratchpad deletion did not. User reloaded the brain in a fresh state and asked "what is this file for?" — the stale draft created uncertainty about whether work was still pending.

**The discipline.** When a draft/scratchpad/staging file gets committed into a canonical destination, delete the draft in the SAME patch as the commit. Don't leave the staging artifact lying around. Stale scratchpads in canonical directories produce exactly the wrong cross-session signal: a future agent (or the user, or future-me) reads them as live pending work when they're actually merged-and-stale.

**Family of patterns this belongs to.** Same family as "real-time essence logging" (brain v2.8 Operating Principle) — both are about closing loops at the time of the change, not at end-of-session. If you stage something for later commit, the deletion of the stage IS part of the commit, not a separate cleanup pass.

**Rule.** When merging a `pending-*.md` or `draft-*.md` or any staging file into a canonical location, the same atomic operation that does the merge also does the cleanup. If the cleanup is "for later," it won't happen.


**Sandbox-blocked-rm workaround (2026-06-13 at ~3:15 PM).** Discovered that the agent sandbox blocks `rm` with "Operation not permitted." This made the merge-time-cleanup discipline harder to enforce directly. The workaround is **tombstone overwrite**: when a stale scratchpad needs to be cleared but cannot be deleted, overwrite the file with a single-paragraph tombstone explaining that the content is merged into the canonical location and the file is safe to delete. Future agents reading the tombstone won't mistake it for pending work, even if the file persists on disk until the user does manual cleanup. Tombstones are not a permanent solution — they're the graceful-degradation move when the cleanup primitive is unavailable.

**Honesty mini-lesson.** When a shell command produces both an error AND a success message (because subsequent `echo` lines run regardless of the failed command), don't claim success. Read the FULL output before reporting. The original 2026-06-13 deletion claim was wrong because the bash output showed `rm: ... Operation not permitted` on one line and a misleading `Removed:` echo on the next, and the report only quoted the echo. Discipline: when reporting on a bash command's outcome, scan all of stderr and the exit code, not just the trailing stdout.

**(2026-06-15 at 9:55 AM)** **Cross-platform Python pitfalls (Round 74).** Three real bugs surfaced when the audit first ran on Windows that wouldn't have surfaced in the sandbox. Codified together because they share a single discipline: write Python that's truly portable, not Linux-portable-in-disguise.

(a) **Text-mode `open()` defaults to the system locale, not UTF-8.** On Linux/Mac, that's typically UTF-8 anyway. On Windows, it's cp1252 (Windows-1252), which fails to decode any UTF-8 multi-byte sequence: em-dashes, smart quotes, escape literals like `\u2014`. The fix is to always specify `encoding='utf-8'` in `open()` calls on text-mode files. Cost of forgetting: a `UnicodeDecodeError` that's instantly fatal on Windows but invisible in dev. Five `open()` calls across `tools/dashboard_integrity.py` and `tools/version_bump.py` were silently broken until the audit's Windows run forced the issue.

(b) **glibc-extension strftime specifiers don't work on Windows.** `%-I`, `%-d`, `%-m`, `%-H`, etc. (the leading-zero-strippers) raise `ValueError: Invalid format string` on Windows strftime. The cross-platform fix is to format manually via arithmetic: `hour_12 = n.hour % 12 or 12` then string-format. Lesson generalizes: avoid the `%-` family of strftime specifiers; format manually where stripping zeros matters.

(c) **`datetime.utcnow()` is deprecated in Python 3.12+.** Not fatal, but emits a noisy `DeprecationWarning` and is scheduled for removal. Replace with `datetime.datetime.now(datetime.timezone.utc)` — timezone-aware and forward-compatible.

The meta-lesson is that cross-platform Python takes ACTIVE discipline; "Python is cross-platform" is a half-truth. The defenses are: (1) always specify `encoding=` on text-mode `open()`, (2) avoid `%-` strftime specifiers, (3) use timezone-aware `datetime.now(tz=...)`, (4) prefer `pathlib` over manual path concatenation, (5) when in doubt, run on Windows once before declaring portable. The audit's `tools_py_parse` invariant catches syntax errors but doesn't catch these runtime portability bugs. Candidate for a future invariant: a `check_no_unsafe_encoding` invariant that scans `tools/*.py` for `open(` calls without `encoding=` (excluding `'rb'` / `'wb'` binary modes).

**(2026-06-15 at 2:45 PM)** **Module-level caches for batch-amortized tools (Round 75 Pass A.3.5).** When a tool's per-call cost is dominated by repeated file IO (like `corpus_search.py` re-reading every book + transcript per query), and the data is read-only within the process, the structural fix is module-level caching with lazy initialization. **Concrete pattern:**
```python
_CACHE = None

def _load_cached():
    global _CACHE
    if _CACHE is not None:
        return _CACHE
    _CACHE = [...load expensive data...]
    return _CACHE
```
Consumer functions call `_load_cached()` at the top instead of re-reading. First call pays the cost; subsequent calls are dict / list lookups.

**Generalizes beyond corpus_search:** any tool that's invoked N times in a batch with the same underlying data substrate is a candidate. The pattern doesn't apply when data freshness matters per call (in which case the cache would lie). For static read-only data like Wallach corpus text, page indexes, manifest CSVs — pure win.

**(2026-06-15 at ~11:55 PM)** **Token-subset matching beats paren-strip equality for keys with form-variant suffixes (Round 97 / Pass E.1.1).** A name-matching primitive that paren-strips both query and key then compares for equality works for `"Vitamin C" ↔ "Vitamin C (Ascorbic Acid)"` (both strip to `"vitamin c"`) but fails on `"Vitamin D3" ↔ "Vitamin D2 (Ergocalciferol) + D3 (Cholecalciferol)"` because paren-stripping the key leaves `"vitamin d2 + d3"` — equal to neither `"vitamin d3"` nor `"vitamin d"`. So `"d3"` matches verbatim against key token `"d3"`, and `"d"` (from `"Vitamin D"`) matches key token `"d2"` via shared base `"d"`. This covers the form-suffix family (`D2`, `D3`, `K1`, `K2`, `B12`, etc.) without per-variant special-casing. Generalizable: when matching against a curated dataset where keys are *descriptive* (parens, plus signs, equals signs, slashes), the matcher's primitive should operate on tokens, not strings.

Guard against trivial single-token queries (< 3 chars) to prevent over-matching — a single-token query of `"C"` shouldn't match the first entry whose key contains a `"c"` token. The matcher's first-stage exact case-insensitive match against the full key (parens included) preserves the precise-match path; token-subset is the second stage; paren-strip equality survives as a third-stage fallback for cases the first two miss. Three stages, ordered from most-precise to most-permissive, with the most-precise wins.

This pattern likely applies anywhere else in the project that does descriptive-key matching — the autonomous loop's invariants and Tacitus's notebook reconciliation are candidates.

## (2026-06-20, Round 158) — forEach exceptions propagate; null-guard every querySelector handler binding after a UI restructure.
