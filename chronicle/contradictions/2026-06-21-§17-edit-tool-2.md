# §17 Incident #2 — Edit-tool truncation of dashboard/package.json

**Date:** 2026-06-21 (Round 1 under §00 discipline · ~3 hours after Incident #1)
**Severity:** Discipline failure — the §17 ban was scope-incorrect; corruption hit a file outside the banned-dirs list
**Status:** Recovered via safe_write.py rewrite; CLAUDE.md never-do #7 widened to cover ALL project files

---

## What happened

While installing the §00 toolchain (task #11), Claude used the Edit tool to expand `dashboard/package.json` from ~360 bytes to ~2 KB (adding 13 new devDeps + 12 npm scripts + simple-git-hooks config + lint-staged config + size-limit config). The Edit tool reported success. The Read tool subsequently showed the full intended content, masking the failure.

When a downstream Python script tried to `json.loads()` the file, it failed at character 504: `Expecting value`. Investigation: actual on-disk size was **506 bytes** — the file was truncated mid-string at `"format": ` (line 12), losing 78% of the intended content. The Read tool was lying about disk state, exactly per the documented Round 74 cache pitfall.

## Why this is the same family as Incident #1

| | Incident #1 (this morning) | Incident #2 (this incident) |
|---|---|---|
| Corruption pattern | Bash `mv` + heredoc chain on Windows mount | Edit tool silent truncation on large expansion |
| Surface affected | `chronicle/archive/current-v3.md` | `dashboard/package.json` |
| Inside banned dirs? | Yes (`chronicle/` *was* `brain/`) | **No** (`dashboard/` root is/was not banned) |
| Detection mechanism | Manual null-byte scan after operation | Downstream JSON parse failure |
| Recovery path | User-provided backup + `safe_write.py rewrite` | In-memory reconstruction + `safe_write.py rewrite` |

**The common shape:** any non-`safe_write.py` write to a project file can silently corrupt. The corruption is filesystem-level + Read-cache-level — orthogonal to which directory the file sits in.

## Root cause of the policy gap

CLAUDE.md never-do #7 (post-Incident-#1) listed specific banned dirs: `memory/`, `knowledge/`, `chronicle/`, `tools/`, `dashboard/assets/styles/design-system.css`, `schemas/`. The implicit assumption: "writes to other dirs (like `dashboard/` root) are safe via Edit/Write tools." That assumption was wrong. The corruption pattern doesn't care about directory taxonomy.

## The fix — codified into CLAUDE.md

**Old text (per-dir list):**
> "No writes to `memory/`, `knowledge/`, `chronicle/`, `tools/`, `dashboard/assets/styles/design-system.css`, or `schemas/` via ANY path other than `tools/safe_write.py`."

**New text (universal):**
> "No writes to any project file under the repo root via ANY path other than `tools/safe_write.py`. ... The ONLY exception: pure scratch space outside the repo (`/tmp/`, the outputs dir)."

The rule now matches the corruption pattern's actual scope. No file inside the project tree is Edit-tool-safe.

## What this proves about the §00 system

**The discipline mechanism worked again:** the downstream JSON parse failure surfaced the corruption within seconds. The build-log entry I had just prepared mentioned `dashboard/package.json` — when the JSON parser fired, recovery was immediate. Defense in depth via Zod-style "validate at the boundary" caught what the Edit tool's success report missed.

**The policy iteration also worked:** Incident #1 widened the ban from "Edit tool only" to "any non-safe_write surface." Incident #2 widened it from "specific dirs" to "any project file." Each incident is sharpening the rule. Future Incident #3 (if any) will have to invent a new corruption surface entirely — both prior gaps are now closed.
