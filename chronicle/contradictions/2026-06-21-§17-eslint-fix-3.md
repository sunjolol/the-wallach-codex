# §17 Incident #3 — `eslint --fix` corruption of creators-log-handler.js

**Date:** 2026-06-21 (Round 1 under §00 discipline · ~5 hours after Incident #1)
**Severity:** Discipline failure — user's `npx eslint --fix` corrupted a project file
**Status:** Recovered via safe_write.py rewrite; the §17 ban scope extends beyond Claude-side tools

---

## What happened

During §00.15·A.1 chunk-close verification, user ran `npx eslint . --fix` on dashboard/. After the run, `npx eslint .` reported a parsing error at `dashboard/creators-log-handler.js:78` — *"Unexpected character ''"*.

Investigation: the file was 3932 bytes on disk, but only the first 3777 bytes contained actual content. Bytes 3778-3932 were 155 null bytes appended after the file's final `})();` line. Classic §17 corruption signature — same shape as Incidents #1 (bash mv + heredoc on Windows mount) and #2 (Edit tool on package.json expansion).

The new wrinkle: this corruption originated from a tool Claude didn't invoke. **`eslint --fix` is a third-party write surface that wrote the corruption.** The §17 ban (per CLAUDE.md never-do #7) covers Claude-side tools (Edit, Write, bash mv, Python open, etc.) but cannot police what npm-installed tools do on the user's filesystem.

## Why this is the same family as Incidents #1 and #2

| | Incident #1 | Incident #2 | Incident #3 |
|---|---|---|---|
| Trigger | bash `mv` + heredoc | Edit tool (large expansion) | `eslint --fix` |
| Surface affected | chronicle/archive/current-v3.md | dashboard/package.json | dashboard/creators-log-handler.js |
| Corruption signature | 1034B content + 52842 nulls | 506B content + truncation | 3777B content + 155 nulls |
| Origin | Claude tool chain | Claude tool chain | User-side npm tool chain |
| Detection mechanism | Manual null-byte scan | JSON parse failure | ESLint parse error |
| Recovery path | User backup → safe_write rewrite | In-memory reconstruction → safe_write rewrite | Truncate-at-first-null → safe_write rewrite |

**The common shape persists:** any write to a project file that doesn't route through `safe_write.py`'s verified atomic-rename pattern can silently corrupt. The corruption pattern is genuinely filesystem-level — not tool-specific, not directory-specific, not even Claude-specific.

## Recovery technique (replicable for future incidents)

```python
data = open(path, 'rb').read()
null_pos = data.find(b'\x00')
if null_pos > 0:
    clean = data[:null_pos].decode('utf-8')
    # Then safe_write.py rewrite with the clean content
```

This works when the corruption is "valid prefix + null tail" (the consistent §17 signature). For more complex corruption patterns, user-provided backup is the recovery path.

## What this means for the §00 system

CLAUDE.md never-do #7 cannot prevent user-side tool corruption — only Claude-tool-side corruption. The defense-in-depth layers that catch user-side corruption are:

1. **Downstream validators** (JSON parse, TypeScript compile, ESLint parse) — they fail loudly when given bad input, surfacing the corruption within seconds of it happening. This caught Incident #3.
2. **The recovery technique above** — any §17 incident with "valid prefix + null tail" shape can be auto-recovered in-place.
3. **Detection invariants** in `tools/invariants.py` (planned for §00.16) — periodic null-byte scans across project files would catch corruption that lingers between active edits.

The discipline mechanism continues to work as designed: failures surface loudly, recovery is documented, the rule sharpens after each incident.
