# §17 Incident #4 — `eslint --fix` corruption of state/coverage.ts (UTF-8 mid-character truncation)

**Date:** 2026-06-21 (Round 1 under §00 discipline · ~6 hours after Incident #1)
**Severity:** Discipline failure — same family as Incident #3 (eslint --fix), new corruption variant
**Status:** Recovered from cached Read-tool content; safe_write.py rewrite restored full file

---

## What happened

During §00.15·B.2 chunk-open, attempting to apply 4 lint fixes to `state/coverage.ts` via Python find-and-replace. Python's `open(..., encoding='utf-8').read()` failed with `UnicodeDecodeError: 'utf-8' codec can't decode bytes in position 2636-2637: unexpected end of data`.

Investigation: the file was only **2638 bytes** on disk (versus the ~6.5KB it should be). The truncation occurred mid-UTF-8 character — the file ends with `\xe2\x94\x80\xe2\x94` which is the start of `─` (U+2500 BOX DRAWINGS LIGHT HORIZONTAL) but missing the third byte. Classic mid-stream truncation, not the null-tail signature of Incidents #1-#3.

The cutoff position: inside the comment header `// ─── Legacy bridge (the strangler-fig wrap) ───` — only ~60 of the file's 222 lines survived.

## Family identification

This is the second `eslint --fix` corruption in one day (after Incident #3 on `creators-log-handler.js`). The family is now confirmed: **`eslint --fix` on the Windows filesystem mount has a corruption-risk pattern.**

Variant differences from prior incidents:

| Incident | Surface | Corruption signature |
|---|---|---|
| #1 | chronicle/archive/current-v3.md | Valid prefix + null tail (52842 nulls) |
| #2 | dashboard/package.json | Mid-string truncation (no nulls) |
| #3 | creators-log-handler.js | Valid prefix + null tail (155 nulls) |
| #4 | state/coverage.ts | **Mid-UTF-8-character truncation** (no nulls, no tail) |

Incident #4 introduces a new variant — truncation that breaks UTF-8 mid-sequence. Detection mechanism differs accordingly: nullbyte scan would NOT catch this; UTF-8 decode failure does.

## Recovery technique

Cached Read-tool content from earlier in the session preserved the canonical 222-line file content. I had read the file just minutes before the corruption was detected, so the full content was still in conversation memory.

The recovery: write the canonical content back via `safe_write.py rewrite`, with the 4 intended lint fixes applied during the rewrite (so the chunk-open work landed in the same atomic operation as the recovery).

## Lessons for the §00 system

**1. The corruption-detection surface needs a UTF-8-validity check.** Existing null-byte scans miss this variant entirely. Adding `python3 -c "open(p, encoding='utf-8').read()"` as part of post-write verification would catch it.

**2. The corruption rate is higher than initially modeled.** Four incidents in one day, from three distinct write surfaces. The §00 substrate (CLAUDE.md never-do #7, safe_write.py, downstream validators) is holding, but the volume suggests the Windows-mount file-write semantics have systemic issues at this session\'s scale.

**3. Cached Read content is a recovery resource.** When the conversation has a recent Read of the corrupted file, the recovery cost is near-zero (already in memory). When it doesn\'t — fall back to user-provided backup (#1) or in-memory reconstruction (#2).

**4. The §17 ban scope is correct but cannot cover every surface.** `eslint --fix` is user-side npm tooling; Claude can\'t police it. The defense that works: every write surface has a downstream validator that fails loud (TypeScript compile, ESLint parse, JSON parse, UTF-8 decode). All four incidents were caught within seconds by some validator, never by Claude proactively scanning.
