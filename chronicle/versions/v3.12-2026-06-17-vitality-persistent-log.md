# Brain v3.12 — Persistent vitality lapse log + in-session re-check (Round 105)

_Round 105. 2026-06-17. Triggered by the user surfacing a 9 AM EDT vitality-check banner ~5 hours after it fired. The agent had no in-session awareness of the lapse because subsequent clean `system_audit.py` runs had overwritten the shared sentinel's `last_lapse_*` fields. The vitality finding was real (essence stale relative to active dashboard work) but invisible to the agent until the user pointed it out._

## What changed

Like v3.11, this is a tool-surface + protocol change, not an agent-reasoning-instruction change. `brain/current.md` text is unchanged. The brain version bumps because the in-session re-check discipline this round codifies is one the agent must follow at every round close — it's part of the closing-move-atomic protocol.

The four-piece structural change:

### 1. `memory/system/vitality-findings.jsonl` — canonical persistent log

Append-only JSONL file. Each line is either an active finding `{ts, kind, summary, status:"active", source}` or a resolution `{ts, kind:"resolution", ref_ts, note}`. The vitality check task owns the write side; the agent owns resolution writes at closing-move; the daily audit reads it via the new invariant. **Audit runs do NOT write to this file** — that's the critical structural protection. The file persists across audit cycles; nothing silently clobbers it.

### 2. `tools/vitality_log.py` — helper tool

Library API + CLI. The vitality SKILL prompt invokes `python3 tools/vitality_log.py append --kind X --summary "..."` to record findings. The agent invokes `python3 tools/vitality_log.py resolve --ts <ts> --note "..."` at closing-move to mark findings resolved. `unresolved` subcommand is CI-friendly (exit 1 if any unresolved, 0 if clean). Centralizes the format and the resolution-tracking logic in one place.

### 3. `check_no_unresolved_vitality_findings` invariant

In `tools/invariants.py`. Severity warning, daily cadence. Fails when an active finding is unresolved AND older than 6 hours. Recent findings (within 6h) are tolerated as in-flight resolution work. The 6-hour threshold matches the realistic cadence between vitality fire and round close. Now 24 daily invariants total.

### 4. Operating-protocols §21

Codifies the in-session re-check discipline: *"Before declaring any round close complete, re-read both `memory/system/audit-sentinel.json` AND `memory/system/vitality-findings.jsonl` for unresolved lapses."* §21 is the in-session real-time defense; the invariant is the audit-layer redundancy. Companion to §1 (closing-move-atomic) and §20 (saga ↔ versions mapping). All three compose: §1 governs what lands in the patch, §20 ensures the journey-timeline projection updates, §21 ensures out-of-band signals don't get lost between session start and round close.

## What the agent does differently

When approaching a closing-move-atomic:

1. **Before declaring the round closed**, run `python3 tools/vitality_log.py unresolved`. If any findings, address them: either resolve (e.g., the work has actually been logged now) via `python3 tools/vitality_log.py resolve --ts <ts> --note "<how>"`, or include the resolution-work in the current closing-move.
2. Re-read `memory/system/audit-sentinel.json` for any `last_lapse_*` fields that weren't there at session start.
3. Then proceed with the standard closing-move-atomic (saga / lessons / decisions / version bump / audit / catchup seal).

This is now part of the closing-move-atomic discipline at the protocol layer — not optional, not ceremony, structural.

## The principle underneath

Same family as Round 45 (single source of truth + propagator) and Round 104 (saga as canonical round source) — applied to a new emerging surface. The structural shape: **two scheduled tasks sharing a write surface is an anti-pattern.** Vitality check and system audit both wrote to `audit-sentinel.json`'s `last_lapse_*` fields. They answer different questions (vitality: is the work being properly logged? audit: are invariants currently passing?). Sharing a sentinel surface implicitly conflated them — clean audit overwrote pending vitality lapse, signal lost.

The defense generalizes: **scheduled tasks that produce findings get their own append-only persistent log; shared sentinels are convenience projections of latest state, NOT canonical records.** Round 105 instantiates this for the vitality check; any future scheduled task that produces findings should follow the same shape.

## The drift surfaces now bounded

Three rounds (45 / 104 / 105) of progressively-tighter cross-system drift defenses:

- **Round 45:** versions.json as the single source of truth for component versions; `version_bump.py` as sole writer; dashboard reads embedded copy. Closed the "three banner-pill places drift independently" failure.
- **Round 104:** saga.md as the canonical source of round numbers; `version_bump.py` reads from it; `check_saga_versions_history_match` invariant catches drift. Closed the "saga round happens without versions bump → off-by-one in history" failure.
- **Round 105:** `vitality-findings.jsonl` as the canonical persistent log for vitality findings; sentinel becomes convenience projection; `check_no_unresolved_vitality_findings` invariant + §21 in-session re-check catch drift. Closed the "scheduled-task signal silently overwritten by audit run" failure.

Each round names a more-specific instantiation of the same underlying principle (canonical records persist; projections are derived and can drift but are reconstructible). The Roman record's reach has been extended at every layer where two systems touch the same surface.
