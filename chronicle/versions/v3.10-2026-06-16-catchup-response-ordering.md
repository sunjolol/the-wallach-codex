# Brain v3.10 — Catch-up response ordering + Tacitus surface priority

**Date adopted:** 2026-06-16 (Round 98)
**Predecessor:** v3.9 (Invariant manifest + system audit + Tacitus folder + meta-auditor, Round 74)
**Trigger:** User spot-check after Round 97's closing-move-atomic surfaced an architectural gap: *"I have a slight concern though: I don't want the 'catch up' command to cause claude to respond back with SO much text that it limits/cuts itself off and doesn't give a full report of EVERYTHING going on. For instance, with this catch up bringing up the save cart idea, AND Tacitus researching before that and potentially writing a very big report himself, I doubt the 'catch up' would preserve the fullness of both things, I'd like to ensure that Tacitus' report is ALWAYS the first thing that is discussed after all checks pass to ensure everything is functioning properly (our major engineering update), THEN if there's ever a situation like this where we want to be reminded of a bigger concept for the next session we keep that as an open thread to be addressed AFTER Tacitus' report."*

---

## What v3.10 adds

A response-structure ordering protocol for the `catch up` trigger, plus addition of the current-month Tacitus notebook to the catch-up read list and seal. The catch-up trigger now actively reads Tacitus's reflection content (not just the sentinel) AND mandates a specific response order so high-stakes surfaces never get crowded out by lower-priority elaborations.

### The new protocol — Phase C / Risk 11 — Response Structure Ordering

Codified in `brain/current.md` alongside the existing Phase B / Risk 9 catch-up integrity defenses. Order is:

1. **Integrity briefing first.** Catchup seal written + briefing-as-proof one-liner-per-file. Terse.
2. **Tacitus surface — second, and FIRST among substantive items.** If `memory/tacitus/YYYY-MM.md` has a reflection dated AFTER the last user activity, present it. Size-aware presentation:
   - Short (≤ ~300 words): surface inline, verbatim or near-verbatim.
   - Long (> ~300 words OR multi-section): condense to (a) one-line theme, (b) 2-4 bullet headlines, (c) explicit *"Full content in `memory/tacitus/YYYY-MM.md` — recommend reading before moving to other items"* framing as the suggested first move for the session.
3. **Open-threads as REMINDERS, not auto-elaborations.** Any `Active` section item gets ONE LINE max — name + status + pointer to its full artifact (e.g., *"Pass F — Save Cartridge active. Full vision in `memory/vision-pass-f-save-cartridge.md`. Ready when you're ready."*). DO NOT proactively elaborate vision artifacts during catch-up.
4. **"What do you want to do?" close.** Hand control to the user.

The principle codified: **catch-up is a briefing room, not a recap.** Briefings name the high-stakes items and where to read more; recaps unpack everything and burn context.

### Catch-up read list extension

`memory/tacitus/YYYY-MM.md` (current-month notebook, derived dynamically) added to the read list in `brain/current.md`. Before v3.10, only the Tacitus sentinel was read on catch-up — the actual reflection content lived in standalone files but was structurally accessible-but-invisible because no read instruction surfaced it.

### Tooling update

`tools/catchup_seal.py` refactored to include the current-month Tacitus notebook in the sealed file list. New `_current_tacitus_notebook()` helper derives the path at run-time so month-rollover doesn't require a code change. New `catchup_files()` accessor returns the live list; both call sites (the seal write loop + `--list` CLI) updated. The `catchup_freshness` invariant now guards 16 files (was 15) including the Tacitus notebook.

### Confirm-or-deny discipline codified

Documented in lessons.md + decisions.md: when the user surfaces an architectural concern, the first move is **investigation + honest report**, not premature fix. Confirm what's in place, deny what's missing, propose the minimal targeted fix, wait for approval before shipping. Triggered by the user's own framing in Round 98: *"I may be overthinking ... Can you confirm or deny this before any action is taken? Is there any legitimate concern that needs to be addressed or is the architecture already in place to take care of my concerns or ensure they're never a real problem to begin with?"*

## Why now

Round 97 had just shipped a comprehensive Pass F vision artifact (`memory/vision-pass-f-save-cartridge.md`) referenced from `open-threads.md` Active section. The user looked one step ahead and saw that the next morning's catch-up — following a Tacitus fire at 5:05 AM that might produce a substantial reflection — would have two surfaces competing for response budget: the Tacitus report and the Pass F vision-artifact reminder. The architecture in place at v3.9 had no guarantee Tacitus would land first, nor any rule keeping vision-artifact pointers from auto-unpacking.

The user's stated requirement was that Tacitus's report ALWAYS comes first after the integrity checks ("our major engineering update"), with reminders following but never crowding it out. v3.10 codifies that requirement as protocol, not best-effort. Architectural concerns named preemptively get architectural fixes preemptively — the same pattern the engineering-safety arc (Round 74) instantiated for failure-mode detection.

---

## What this doesn't change

- The Phase B / Risk 9 catch-up integrity defenses (catchup seal + briefing-as-proof) stay intact.
- The `catchup_freshness` audit invariant stays intact; its file count expanded by one to include the Tacitus notebook.
- Tacitus's write-boundary (notebook-only) stays unchanged.
- The brain's other triggers (`dashboard`, wrap-up signal detection) stay unchanged.

---

## Forward implication

When future autonomous-write surfaces are added (a new persistent output from a scheduled task, a new sentinel, a new artifact), the v3.10 pattern is: (a) add the file to the catch-up read list, (b) add a briefing-as-proof citation row, (c) decide where it fits in the response-structure ordering protocol, (d) add it to `catchup_seal.py`. Four touchpoints, all atomic in the same patch. Codified in lessons.md under "Standalone-file persistence is necessary but not sufficient for cross-session continuity."
