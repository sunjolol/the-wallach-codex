_Round 108. 2026-06-17. ## What changed

Tool-surface + protocol change. `brain/current.md` text is unchanged. The brain version bumps because the closing-move discipline this round codifies governs every future round that executes (or rejects, defers) a Cura/Vision finding.

### 1. `memory/system/implementations.jsonl` — canonical persistent log

Append-only JSONL. Each line records one outcome decision: `{ts, source_date, source_mode, source_session, candidate, status, round, summary}`. Status enum: `implemented` / `in_progress` / `rejected` / `deferred`. Status transitions over time are recorded as separate appends; the latest entry for a `(source_date, source_mode, source_session, candidate)` tuple is the current status.

### 2. `tools/implementation_log.py` — helper tool

Library API (`append_entry`, `latest_status`, `all_entries`, `by_source`) + CLI (`append` / `list` / `query` / `latest`). Schema validation in the tool; arbitrary writes from elsewhere are not sanctioned.

### 3. `check_implementations_log_well_formed` invariant

In `tools/invariants.py`. Severity warning, daily cadence. Verifies every entry's `(source_date, source_mode, source_session)` tuple references a real notebook session header. Orphan entries fail the audit. Now 26 daily invariants total.

### 4. Build script integration

`tools/build_tacitus_dashboard_live.py` `_attach_implementations()` joins log entries to deepen survivors via `latest_status()`. Match is case-insensitive prefix on the first 60 characters of the candidate title — tolerates light editing.

### 5. Dashboard render

`renderImplBadge()` JS function emits a mode-tinted FF-vibe save-crystal SVG next to the LAND badge. Filled+checkmark for `implemented` (Cura gold / Vision cyan; drop-shadow glow). Half-filled+dot for `in_progress`. Dashed-outline+X for `rejected`. Faint outline+dot for `deferred`. Hover surfaces round + summary via `title` attribute.

### 6. Operating-protocols §24

Closing-move discipline: when a round implements / rejects / defers / moves to in_progress on a Cura or Vision finding, the closing-move-atomic includes a `python tools/implementation_log.py append` call in the same patch. **The agent never writes implementation status without user direction.**

## What the agent does differently

When closing a round that touches a Cura/Vision finding:

1. Append the saga / lessons / decisions entries (§1 unchanged).
2. **Run the implementation log append (§24 new)**: `python tools/implementation_log.py append --source-date YYYY-MM-DD --source-mode <Cura|Vision> --source-session N --candidate "title" --status <implemented|rejected|deferred|in_progress> --round N --summary "..."`.
3. Run the downstream-sweep (§1 bullet 6).
4. Then proceed with version_bump, integrity restore, audit, catchup seal.

The user's explicit approval is the source of truth for status. Agent NEVER invents an `implemented` status — it records what the user said.

## The agent's authority boundary, named

The agent's role in the implementation log is **scribe**, not **decider**. The user is the only authority for marking something implemented / rejected / deferred / in_progress. The agent's job:

1. Execute the work after user approval (as it always has).
2. Record the user's decision in the log at the moment the closing-move happens.
3. NEVER invent a status on its own initiative — even when the work is clearly done, wait for the user's explicit approval signal before recording.

This is the same architectural pattern as Tacitus's write boundary (§4): autonomous-system findings live in their own surface; user-managed canonical decisions live in another surface; the boundary between them is sacred.
